# W11 — 환경변수 통합 (.env 단일화)

> **상태**: ✅ 완료  
> **기간**: W10 완료 후

---

## 목표

프론트엔드(Vite), Spring Boot, FastAPI, Docker Compose에 흩어져 있던 환경변수를 프로젝트 루트 `.env` 단일 파일로 통합. `.env.example` 템플릿으로 신규 개발자의 온보딩 간소화.

---

## 배경

W10까지 구현 완료 후 실 API 키(국토부, Kakao/Google OAuth2, OpenAI)가 없어 미검증된 기능들이 다수 남아 있었다. 각 키를 어디에 넣어야 하는지가 분산되어 있어 온보딩이 번거로웠다:

- Vite 환경변수: `VITE_*` 접두사로 `.env.local` 에 관리
- Spring Boot: `application-local.yml`에 하드코딩(`username: root`, `password: root`)
- FastAPI: `backend/.env`에 별도 관리 (`load_dotenv()` → CWD 탐색)
- Docker Compose: 일부 변수 하드코딩, 일부는 `${VAR:-default}` 형식

---

## 변경 파일

| 파일 | 변경 유형 | 내용 |
|------|----------|------|
| `.env.example` | **재작성** | 모든 서비스 변수를 섹션별로 통합한 완전한 템플릿 |
| `backend-spring/.../application-local.yml` | **수정** | `username: root` → `${DB_USERNAME:root}`, `password: root` → `${DB_PASSWORD:root}` |
| `docker-compose.yml` | **수정** | `DB_USERNAME` 하드코딩 제거, `DB_PASSWORD` 변수화, OAuth2 키 4개 추가, `ALLOWED_ORIGINS` 변수화 |
| `backend/main.py` | **수정** | `load_dotenv()` → 루트 `.env` 우선 탐색 후 없으면 CWD `.env` 폴백 |
| `Makefile` | **수정** | DB 변수 `.env`에서 읽기, `spring`/`fastapi` 타겟에 `.env` 자동 소싱 추가 |
| `backend/.env.example` | **수정** | "루트 `.env` 사용" 안내로 교체 |

```

CHATBOT_URL

# 프론트엔드 (Vite)

# Docker Compose
FRONTEND_URL, ALLOWED_ORIGINS
```

## 각 서비스의 .env 읽기 방식

| 서비스 | 읽기 방식 | 비고 |
|--------|----------|------|
| **Vite** | 자동 (`.env` 파일 기본 지원) | `VITE_` 접두사 변수만 브라우저에 노출 |
| **Spring Boot** | `${VAR_NAME:default}` 표기로 시스템 환경변수 읽기 | Makefile이 `set -a; . .env` 로 소싱 후 프로세스 실행 |
| **FastAPI** | `main.py`에서 `load_dotenv(루트/.env)` | Docker에서는 `environment:` 섹션으로 주입 |
| **Docker Compose** | `${VAR:-default}` 표기로 `.env` 파일 자동 참조 | Compose는 `docker-compose.yml` 위치의 `.env`를 자동 로드 |
| **Makefile** | `$(shell grep '^KEY=' .env ...)` 으로 파싱 | `make spring`, `make fastapi` 실행 시 `set -a; source .env` |

```bash
# 2. 실제 키 입력 (최소한 OPENAI_API_KEY 입력 시 챗봇 활성화)

# 3. 개발 환경 시작

```

## 트러블슈팅 기록

### [T-01] 카카오 OAuth2 로그인 후 UNAUTHORIZED 오류

**발생 일자**: 2026-05-30  
**증상**: 카카오 동의 화면 → 인가 코드 콜백 → Spring 처리 후 프론트엔드가 `{"success":false,"error":{"code":"UNAUTHORIZED","message":"인증이 필요합니다."}}` 반환. 로그인이 완료되지 않고 리다이렉트 실패.

---

#### 원인

`application-prod.yml`에 카카오 OAuth2 등록에서 `client-authentication-method` 필드가 누락되어 있었다.

```yaml
# application-prod.yml (수정 전 — 문제 있음)
kakao:
  client-id: ${KAKAO_CLIENT_ID:}
  client-secret: ${KAKAO_CLIENT_SECRET:}
  redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
  authorization-grant-type: authorization_code
  # client-authentication-method 누락!
  scope: profile_nickname
```

Spring Security OAuth2의 기본값은 `client_secret_basic`으로, 클라이언트 ID/시크릿을 **HTTP Basic Auth 헤더**(`Authorization: Basic ...`)에 담아 토큰 엔드포인트에 전송한다. 그러나 카카오 토큰 엔드포인트(`https://kauth.kakao.com/oauth/token`)는 **요청 바디**에 `client_id`/`client_secret`을 넣는 `client_secret_post` 방식만 허용한다.

결과적으로 카카오 토큰 교환 요청이 `401 Unauthorized`로 실패하고, Spring Security는 인증 실패로 간주하여 `/login?error`로 리다이렉트했다. 반면 `application-local.yml`에는 `client-authentication-method: client_secret_post`가 이미 명시되어 있어 로컬(`make dev`) 환경에서는 문제가 없었다.

**디버깅 단서**: `docker-compose.yml`에 `LOGGING_LEVEL_ORG_SPRINGFRAMEWORK_SECURITY: DEBUG` 추가 후 로그 확인:
```
Authentication failed with provider OAuth2LoginAuthenticationProvider since
[invalid_token_response] An error occurred while attempting to retrieve
the OAuth 2.0 Access Token Response: 401 : [no body]
```

---

#### 해결

**1. `application-prod.yml` — `client-authentication-method` 추가**

```yaml
# application-prod.yml (수정 후)
kakao:
  client-id: ${KAKAO_CLIENT_ID:}
  client-secret: ${KAKAO_CLIENT_SECRET:}
  redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
  authorization-grant-type: authorization_code
  client-authentication-method: client_secret_post   # ← 추가
  scope: profile_nickname
```

**2. `src/pages/LoginScreen.jsx` — OAuth2 진입 전 기존 세션 초기화**

OAuth2 리다이렉트 전 Zustand 스토어에 남아 있던 만료 토큰이 콜백 복귀 후 `hydrateFromServer()` 호출 시 401을 유발할 수 있는 경쟁 조건 차단:

```javascript
// 수정 전
const handleOAuth2 = (provider) => {
    window.location.href = `${API_BASE}/oauth2/authorization/${provider}`;
};

// 수정 후
const handleOAuth2 = (provider) => {
    clearAuth();   // localStorage 토큰 + Zustand authUser 모두 초기화
    window.location.href = `${API_BASE}/oauth2/authorization/${provider}`;
};
```

**3. Docker 이미지 재빌드**

`application-prod.yml` 변경은 JAR에 번들되므로, 환경변수 주입과 달리 컨테이너 재시작만으로는 반영되지 않는다. 반드시 재빌드 필요:

```bash
docker compose build spring
docker compose up -d spring
```

---

#### 재발 방지

- `application-local.yml`과 `application-prod.yml`의 OAuth2 registration 블록을 수정할 때는 두 파일을 동시에 확인한다.
- 카카오 OAuth2는 `client_secret_post` 방식 필수. `client-authentication-method` 필드를 생략하면 Spring 기본값(`client_secret_basic`)이 적용되어 카카오 토큰 교환이 실패한다.
- OAuth2 관련 문제 진단 시 `LOGGING_LEVEL_ORG_SPRINGFRAMEWORK_SECURITY: DEBUG`를 docker-compose.yml에 임시 추가하면 정확한 실패 원인이 로그에 출력된다 (디버깅 후 INFO로 되돌릴 것).

### [T-02] Google OAuth2 로그인 500 Internal Server Error

**발생 일자**: 2026-05-30  
**증상**: Google 동의 화면 → 인가 코드 콜백(`/login/oauth2/code/google`) → Spring에서 500 반환. Whitelabel Error Page 노출.

---

#### 원인

Google은 scope에 `openid`가 포함되므로 **OIDC(OpenID Connect)** 프로토콜로 처리된다. Spring Security는 OIDC 공급자에 대해 `OidcUserService`를 사용하는데, SecurityConfig에 `.userService(customOAuth2UserService)`만 등록되어 있었다.

`.userService()`는 **비-OIDC OAuth2 전용** 훅이다. Google 콜백 시 Spring은 기본 `OidcUserService`를 호출하여 인증을 완료하지만, 우리의 `CustomOAuth2UserService.loadUser()`는 **호출되지 않는다**. 결과:

- DB에 Google 유저가 저장되지 않음
- `OAuth2User` 어트리뷰트에 `_userId`가 주입되지 않음
- `OAuth2SuccessHandler`에서 `oAuth2User.getAttributes().get("_userId")` → `null`
- `userMapper.findById(null)` → `null`
- `authService.issueTokens(null)` → NPE

```
java.lang.NullPointerException: Cannot invoke "User.getId()" because "user" is null
    at AuthService.issueTokens(AuthService.java:89)
    at OAuth2SuccessHandler.onAuthenticationSuccess(OAuth2SuccessHandler.java:36)
```

**OIDC 판별 기준**: scope에 `openid`가 포함되면 Spring Security가 OIDC 경로로 처리한다.

```yaml
kakao:
  scope: profile_nickname        # openid 없음 → 일반 OAuth2 → .userService() 호출됨
google:
  scope: openid, profile, email  # openid 있음 → OIDC → .oidcUserService() 호출됨
```

---

#### 해결

**1. `CustomOidcUser.java` 신규 생성**

`DefaultOidcUser`를 상속해 `userId` 필드를 추가한 래퍼 클래스. OIDC 인증 결과에 DB의 유저 ID를 실어 `OAuth2SuccessHandler`까지 전달한다.

```java
public class CustomOidcUser extends DefaultOidcUser {
    private final Long userId;
    // ...
    public Long getUserId() { return userId; }
}
```

**2. `CustomOidcUserService.java` 신규 생성**

`OAuth2UserService<OidcUserRequest, OidcUser>`를 구현. `OidcUserService`에 위임 후 DB upsert → `CustomOidcUser` 반환.

```java
@Service
public class CustomOidcUserService implements OAuth2UserService<OidcUserRequest, OidcUser> {
    public OidcUser loadUser(OidcUserRequest userRequest) {
        OidcUser oidcUser = new OidcUserService().loadUser(userRequest);
        User user = upsertUser(...);  // DB 저장/조회
        return new CustomOidcUser(..., user.getId());
    }
}
```

**3. `SecurityConfig.java` — `.oidcUserService()` 등록**

```java
.oauth2Login(oauth -> oauth
    .userInfoEndpoint(u -> u
        .userService(customOAuth2UserService)      // Kakao (비-OIDC)
        .oidcUserService(customOidcUserService))   // Google (OIDC) ← 추가
    .successHandler(oAuth2SuccessHandler)
)
```

**4. `OAuth2SuccessHandler.java` — 두 경로 분기 처리**

```java
Long userId;
if (oAuth2User instanceof CustomOidcUser customOidcUser) {
    userId = customOidcUser.getUserId();           // OIDC 경로 (Google)
} else {
    userId = (Long) oAuth2User.getAttributes().get("_userId");  // 일반 OAuth2 경로 (Kakao)
}
```

---

#### 재발 방지

- **신규 OAuth2 공급자를 추가할 때**: scope에 `openid`가 있으면 `.oidcUserService()`를 구현해야 한다. `.userService()`만으로는 OIDC 공급자가 처리되지 않는다.
- Kakao도 `openid` scope를 추가하면 OIDC 경로로 전환된다. 현재는 `profile_nickname`만 사용 중이므로 비-OIDC로 처리된다.
